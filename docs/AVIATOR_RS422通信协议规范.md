# AVIATOR 飞控—机器人双冗余 RS422 通信协议规范

定义 **REQUEST、REPLY、CONTROL、STATUS 四种消息**。REQUEST/REPLY 用于离散操作的一问一答；CONTROL 和 STATUS 分别以 **50 Hz（20 ms 周期）**连续发送，不逐帧回复。STATUS 一帧包含系统状态、双臂及双手关节位置、方向盘检测状态，不分页、不轮流发送设备。

依据：[软件架构设计](AVIATOR机器人驾驶飞机控制系统软件架构设计方案.md)、[内部 ZMQ 协议](AVIATOR_ZMQ协议格式说明.md)、[目录与迁移说明](项目目录与迁移说明.md)。本文定义外部串口协议，不修改内部 ZMQ 格式。字段分配、量化精度、硬件参数及超时值是待双方冻结的设计；当前项目尚未实现本文串口运行入口。

## 1. 接口和总体规则

- A/B 是两套独立的全双工 RS422，各有独立 UART、收发器和线缆；每路包含飞控发送、机器人发送两个差分对。
- 串口建议 921600 bit/s、8N1，无软件/硬件流控；连接器、隔离、终端及接地由硬件接口文件约定。
- 飞控将同一逻辑 REQUEST/CONTROL 原样复制到 A/B；机器人将同一逻辑 REPLY/STATUS 原样复制到 A/B。两路字节完全一致，物理端口区分 A/B。
- CONTROL：飞控→机器人，50 Hz；STATUS：机器人→飞控，50 Hz。在待机、故障和动作执行期间也持续发送，未授权的 CONTROL 不驱动机器人。
- 不发送独立的心跳、握手、时间同步、设备分包、视觉分包、诊断或结果查询消息。双方通过周期消息判断链路存活，通过 STATUS 的状态、阶段和错误码观察动作进展。
- 协议布局、设备关节顺序、坐标系、量纲和超时参数线下配置一致，不在线协商。本文无公共数据前缀，每类 DATA 直接按对应表编码。

## 2. 帧格式

```text
FF FE | LEN (1 byte) | TYPE (1 byte) | DATA (LEN−5 bytes) | SUM (1 byte)
```

| 整帧偏移 | 字节数 | 字段 | 定义 |
| ---: | ---: | --- | --- |
| 0 | 2 | 帧头 | 固定 `FF FE`。 |
| 2 | 1 | LEN | 整帧总字节数，包含帧头至校验和，最大 255；0 不代表 256。 |
| 3 | 1 | TYPE | 四种消息之一，见下表。 |
| 4 | LEN−5 | DATA | 对应消息的数据。 |
| LEN−1 | 1 | SUM | LEN、TYPE、DATA 各无符号字节累加的低 8 位。 |

```text
SUM = (LEN + TYPE + 所有 DATA 字节之和) & 0xFF
```

帧头及 SUM 本身不参与计算，不取反、不取补码，不使用 CRC、转义或额外帧尾。DATA 中允许原样出现 `FF FE`。累加和不能检出字节交换或相互抵消的全部多字节错误；接收方仍须检查长度、范围、时间戳及双路一致性。

多字节整数一律小端，有符号整数采用补码；结构连续打包，无编译器填充。后文偏移均相对 DATA 起点，换算整帧偏移需加 4。

| TYPE | 名称 | 方向 | DATA 字节 | LEN（十进制/十六进制） | 发送方式 |
| --- | --- | --- | ---: | --- | --- |
| `0x01` | REQUEST | 飞控→机器人 | 5 | 10 / `0x0A` | 离散操作请求。 |
| `0x02` | REPLY | 机器人→飞控 | 8 | 13 / `0x0D` | 每次 REQUEST 对应一条逻辑应答。 |
| `0x03` | CONTROL | 飞控→机器人 | 9 | 14 / `0x0E` | 50 Hz，无回复。 |
| `0x04` | STATUS | 机器人→飞控 | 77 | 82 / `0x52` | 50 Hz，无回复。 |

接收端在有界缓冲中搜索帧头，先检查 TYPE 与固定 LEN 是否匹配，再按 LEN 收齐并校验；正常候选帧内的 `FF FE` 不另起一帧。格式/校验失败或从候选帧头起 50 ms 未收齐，从该候选帧头的下一字节重新扫描缓存，避免错误长度吞掉下一合法帧。校验通过但业务非法的帧整体拒绝，不重新扫描其数据为命令。须支持跨次读取、粘包和连续噪声。

### 2.1 运行毫秒计数（4 字节）

所有保留的 `timestamp_ms` 字段（包括 last_control_timestamp_ms）均为 **uint32、4 字节、小端序**。REQUEST、CONTROL、STATUS 的 timestamp_ms 取消息首次生成时，本端通信程序从本次运行开始经过的毫秒数：

```text
timestamp_ms = floor((monotonic_now − run_start) / 1 ms) mod 2^32
```

- 启动时从 0 计时，每毫秒加 1；不是每发一帧只加 1。50 Hz 周期帧通常相差 20 ms。使用单调时钟，不受 UTC 校时影响；程序重启后重新从 0 计时，不持久化计数。
- 飞控 REQUEST/CONTROL 使用同一本端运行计时器，机器人 STATUS 使用机器人端运行计时器。两端起点独立，不能相减求延迟。REPLY 原样回显 REQUEST 的 timestamp_ms，不填机器人当前运行时间；last_control_timestamp_ms 同样回显已接纳 CONTROL 的值。
- 同一类型的新逻辑消息在同一毫秒内最多生成一条，需要时等待下一毫秒；不同类型允许相同时间戳，接收端按类型分别维护基准。A/B 副本及重试保持原帧和原时间戳，不重新取时。
- 约每 49.7 天从 `0xFFFFFFFF` 回绕到 0，0 是合法值。新旧比较使用 `delta=(new-old)&0xFFFFFFFF`：0 为重复，`0<delta<0x80000000` 为更新，其他值为旧值或歧义，不直接用整数大小比较。有效比较跨度必须小于约 24.9 天。
- 周期流长时间中断或某类请求基准超过上述半周期时，停止接纳相关新业务，按第 7 节受控恢复流程重建基准。缓存记录也须限定在本次运行连接及有限时间窗口内，不能把上一圈或上次运行的相同数值当作同一请求。
- 本协议无启动标识，单靠线上时间戳无法可靠区分重启、回绕和旧消息。任一端通信程序或 Core 重启后均须先停止操控，双方协调清空旧队列、取消旧请求重试并重建接收基准，再恢复业务；不得收到小时间戳就自动清基准继续执行。

## 3. REQUEST / REPLY：离散操作一问一答

### 3.1 REQUEST（5 字节）

| 偏移 | 类型 | 字段 | 说明 |
| ---: | --- | --- | --- |
| 0 | u32 | timestamp_ms | 飞控生成的本次请求时间戳，重试保持不变。 |
| 4 | u8 | operation | 下表操作码。 |

| operation | 名称 | 允许状态 / 作用 |
| --- | --- | --- |
| `0x01` | ENTER_STANDBY | 已退出接触的待机状态可幂等确认；不隐含松手、回零或断电。 |
| `0x02` | GRASP_WHEEL | STANDBY→GRASPING→FOLLOWING，执行抓方向盘程序。 |
| `0x03` | START_CONTROL | FOLLOWING→CONTROL，成功后开始接收本次操控的新目标。 |
| `0x04` | EXIT_CONTROL | CONTROL→STOPPING→FOLLOWING；已处于 FOLLOWING 可幂等确认。 |
| `0x05` | LEAVE_WHEEL | FOLLOWING→RELEASING→STANDBY；CONTROL 下须先退出操控。 |
| `0x06` | RESET_ERROR | 在故障原因解除且本地允许时复位至 SAFE/STANDBY；不解除硬件急停，不自动恢复操控。 |

其余操作码保留。状态与动作完成依据由 Core 决定，网关不自行执行机器人动作。

### 3.2 REPLY（8 字节）

| 偏移 | 类型 | 字段 | 说明 |
| ---: | --- | --- | --- |
| 0 | u32 | timestamp_ms | 原样回显 REQUEST 的时间戳，用于匹配应答。 |
| 4 | u8 | operation | 原样回显操作码。 |
| 5 | u8 | result | 1 ACCEPTED 已受理；3 COMPLETED 已同步完成；4 REJECTED 拒绝。 |
| 6 | u16 | error_code | 成功为 0，拒绝原因见第 8 节。 |

一次 REQUEST 只产生一条逻辑 REPLY，复制到 A/B。长动作只回复 ACCEPTED，后续通过 STATUS 的 state、phase 和错误码观察当前进展，不额外发送完成 REPLY。REPLY 表示真实的 Core 受理或同步完成，不能以写入 ZMQ 队列成功代替。

### 3.3 重试与动作观察

- 建议等待应答 100 ms，最多原帧重试 3 次；重试 timestamp_ms 和内容完全不变。飞控按当前未完成请求的时间戳及 operation 匹配 REPLY，忽略双路重复副本，不接受历史未匹配应答。
- 本次运行连接内，机器人按请求时间戳去重，保存原请求及原始 REPLY。同时间戳同内容重发原应答，同时间戳不同内容拒绝。先查缓存，再按第 2.1 节模运算比较 REQUEST 高水位；没有缓存的旧请求拒绝，不重新执行。
- 原请求及应答建议保留 10 分钟，至少覆盖全部重试窗口；缓存过期不清 REQUEST 高水位。容量不足则拒绝新请求。动作开始前先登记去重记录；运行期同一请求只派发一次。请求基准老化至半周期前需受控重建；重启后的新连接不继承旧连接的时间戳去重表。历史执行日志可保留作人工核对，但不按时间戳跨运行自动匹配。
- 同时只允许一个普通状态修改操作；安全退出可中止操控开始流程。新受理操作更新 STATUS.operation，拒绝请求不覆盖它。该字段只表示最近受理的操作类别，不能唯一关联一次请求。
- 收到匹配的 ACCEPTED 后，飞控结合后续有效 STATUS 的 operation、state、phase、current_error_code 观察动作是否到达约定目标状态。STATUS 不提供逐请求完成结果，不能仅凭相同 operation 或相同目标状态确认某次未获应答请求已执行；需要严格逐事务最终结果时须另行扩展协议。
- 应答超过重试次数仍未收到，或任何一端重启时，将未决动作视为结果未知；核对实际状态，不自动生成新时间戳重做。恢复时先停止重试、清空双方积压并建立新运行连接，再由受控流程决定后续操作。

## 4. CONTROL：完整控制指令，50 Hz

DATA 固定 9 字节，一帧同时发送 roll 和 pitch。

| 偏移 | 类型 | 字段 | 说明 |
| ---: | --- | --- | --- |
| 0 | u32 | timestamp_ms | 飞控本周期生成的自增时间戳，A/B 相同。 |
| 4 | i16 | roll_q | [-10000,10000]，实际百分比值为 roll_q/10000。 |
| 6 | i16 | pitch_q | [-10000,10000]，实际百分比值为 pitch_q/10000。 |
| 8 | u8 | valid | 0 无有效控制，1 有效；其他值非法。 |

示例：roll=0.35、pitch=-0.12 编码为 3500、-1200。它们是 [-1,1] 的归一化操纵量，不是关节角度。正方向、零点和机械行程映射线下冻结。越界拒绝，不静默限幅。

只有 Core 处于 CONTROL，且递增时间戳、valid 和范围均合法时才接纳执行。待机仍发 CONTROL，valid=0；valid=0 不表示零目标，不刷新有效控制超时。

飞控收到 START_CONTROL 的匹配 ACCEPTED/COMPLETED 应答，并观察到有效 STATUS.state=CONTROL 后，再生成新的有效控制帧。机器人对首条目标按第 2.1 节模运算检查其时间戳晚于本次 START_CONTROL 请求、且晚于此前 CONTROL 接收高水位；后续仅与最近 CONTROL 基准比较，不长期与最初开始时间比较。非操控状态也维护 CONTROL 接收高水位，但不缓存目标供以后执行。开始后 100 ms 内没有首条有效目标则退出操控并进入安全处理。

退出、失联、网关或 Core 重启、故障时关闭操控接纳并清理待执行目标，恢复后需新的 START_CONTROL，不自动恢复旧目标。本版不包含独立操控标识；尚未收到的延迟帧不能仅凭时间戳完全证明属于当前操控，因此仍须遵守清队列、受控恢复及第 7 节延迟约束。

CONTROL 不携带状态切换命令，切换统一使用 REQUEST。不逐帧 ACK；STATUS 的 last_control_timestamp_ms 仅表明 Core 已接纳的最近时间戳，不表示物理动作到位。

## 5. STATUS：全部状态单帧，50 Hz

### 5.1 固定布局与容量

本版采用项目内部协议的示例规模：**左右臂各 7 关节、左右手各 6 个反馈关节**。实际手部自由度与反馈能力须在设备选型后核实；六通道驱动量不能冒充完整物理关节。使用定点整数使必要反馈全部装入一帧，不采用浮点、分页或省略某一设备。

| DATA 偏移 | 字节数 | 内容 |
| ---: | ---: | --- |
| 0 | 17 | 系统状态。 |
| 17 | 14 | 左臂：7 个关节位置。 |
| 31 | 14 | 右臂：同上。 |
| 45 | 12 | 左手：6 个关节位置。 |
| 57 | 12 | 右手：同上。 |
| 69 | 8 | 相机定位与方向盘检测状态。 |
| 合计 | **77** | 加外层 5 字节，整帧 **82 字节**。 |

每 20 ms 取 Core 最近聚合快照，完整编码所有区块并复制到双路。串口发布 50 Hz 不等于各传感器都产生 50 Hz 新测量；各测量的原始采样时效由机器人内部检查，过期或不可用字段填无效值；不能仅更新整帧时间戳伪装新测量。各设备实测时刻可以不同，不宣称所有测量硬件同步。

### 5.2 系统状态（17 字节）

| 偏移 | 类型 | 字段 | 说明 |
| ---: | --- | --- | --- |
| 0 | u32 | timestamp_ms | 机器人本次运行起的毫秒计数。 |
| 4 | u32 | last_control_timestamp_ms | Core 最近接纳的 CONTROL 时间戳；是否存在由 flags bit1 表示。 |
| 8 | u8 | state | 运行状态，见第 6 节。 |
| 9 | u8 | phase | 当前动作阶段，见第 6 节。 |
| 10 | u16 | current_error_code | 当前最高优先级错误，0 无错误。 |
| 12 | u16 | last_error_code | 上次非零错误，故障解除后保留。 |
| 14 | u8 | active_link | 0 无、1 A、2 B。 |
| 15 | u8 | flags | bit0 系统快照有效；bit1 本次操控期间接纳过有效控制；bit2 A 接收健康；bit3 B 接收健康；bit4 冗余降级；bit5 双路冲突锁存；bit6 动作仅由软件完成确认；bit7 保留 0。 |
| 16 | u8 | operation | 最近已受理操作类别，无为 0；不表示某次请求的完成结果。 |

开始新操控或退出操控时，last_control_timestamp_ms 清零且清 bit1；bit1=1 时该时间戳可以合法为 0（启动或回绕），不能用数值是否为零判断有效。timestamp_ms 属于机器人时钟域，last_control_timestamp_ms 回显飞控时钟域的值，不允许相减计算延迟。启动后未知的历史错误用 `0x1FFD` 表示，不能用 0 冒充从未出错。Core 数据过期时清系统有效位，由机器人内部检查时效，不再发送快照年龄。

### 5.3 设备区块：仅双臂、双手关节位置

双臂、双手均只发送关节位置数组，不发送单设备状态、年龄、关节速度或末端位置/姿态。

**关节位置的每个元素为 2 字节有符号 `int16_t`（表中 i16），小端序，不是 4 字节 float。** 解码时先读小端 int16，再按比例转换为物理量；不能直接按 IEEE 754 float32 解释线上字节。

| 设备区块 | 块内偏移 | 类型 | 字段 | 字节数 / 单位 |
| --- | ---: | --- | --- | --- |
| 左臂、右臂，各一块 | 0 | i16[7] | joint_position | 每臂 14 字节；编码值×0.001 rad。 |
| 左手、右手，各一块 | 0 | i16[6] | joint_position | 每手 12 字节；物理关节模式为编码值×0.001 rad。 |

例如关节位置 1.234 rad 编码为 1234，线上字节 `D2 04`；-0.500 rad 编码为 -500，线上字节 `0C FE`。

- `-32768` 表示无效；有效物理位置编码范围 [-32767,32767]。超量程报告无效，不饱和为边界值。不支持或未安装设备的数组仍保留并填无效，不能用零冒充实测。
- 编码四舍五入到最近整数，恰好半整数时向远离 0 方向取整。
- 臂反馈顺序为冻结的 J1..J7；手为冻结的 J1..J6。手若仅提供归一化驱动量，线下配置必须明确手区块采用 q/10000，编码范围 0..10000；线上仍为 int16，不能将其宣称为物理角度反馈。单位模式不得运行时静默改变。
- 只发送实际反馈位置，不用指令目标冒充测量。同一设备数组来自同一源样本；单个关节无效不必抹掉其他有效关节。
- 机器人内部检查双臂、双手的采样时效，源离线或超过约定时效时将对应位置置无效。设备故障通过系统 current_error_code/last_error_code 的左右臂、左右手错误域报告。飞控不能从本版读取四设备各自样本年龄。

总 DATA 容量公式为 `25+2×四设备关节总数`，本版 26 个关节得到 77 字节。实际关节数变化时须重新冻结固定布局，不能单方增加字段、截断数组或分页。本版保持 int16 定点编码，不因删减字段而自动改为 float32。

### 5.4 相机与方向盘检测（8 字节）

| 块内偏移 | 类型 | 字段 | 说明 |
| ---: | --- | --- | --- |
| 0 | u8 | vision_state | 0 离线、1 初始化、2 搜索、3 跟踪、4 丢失、5 错误。 |
| 1 | u8 | flags | bit0 定位有效；bit1 检测到方向盘；bit2 置信度有效；其他位 0。 |
| 2 | u16 | confidence_q | 0..10000，除以 10000 为 [0,1]；65535 未知。 |
| 4 | i16 | yoke_roll_q | 方向盘实测归一化 roll；类型、字节序及比例与 CONTROL.roll_q 一致。 |
| 6 | i16 | yoke_pitch_q | 方向盘实测归一化 pitch；类型、字节序及比例与 CONTROL.pitch_q 一致。 |

方向盘状态由 vision_state、flags、置信度及实测 roll/pitch 共同表达。STATUS 报告方向盘当前检测值，CONTROL 发送目标指令值，不能将 CONTROL 原样回填为实测状态。

| 共同约定 | CONTROL.roll_q / pitch_q | STATUS.yoke_roll_q / yoke_pitch_q |
| --- | --- | --- |
| 线上类型 | 2 字节有符号 int16，小端 | 相同。 |
| 有效编码范围 | [-10000,10000] | 相同。 |
| 解码 | 编码值/10000，得到 [-1.0,1.0] | 相同。 |
| 方向与量纲 | 无量纲百分比；零点、正负方向和满量程行程线下冻结 | 与 CONTROL 使用同一映射；视觉输出角度/位移须先转换。 |
| 数值示例 | roll=0.35→3500→`AC 0D`；pitch=-0.12→-1200→`50 FB` | 相同数值对应完全相同的字节。 |
| 无效表达 | valid=0；roll/pitch 仍须在规定范围内，禁止把 -32768 当指令 | 无效测量为 -32768（`00 80`），并清 flags bit0；无效值不参与控制比较。 |

原始图像及检测结果的时效由机器人内部检查，不在串口发送样本年龄。飞控依据有效位和 STATUS 接收超时使用结果，不能从本帧反推出原始采样时间。仅当 flags bit0/bit1 均为 1、两个操纵量在有效范围内且样本未过期时，方向盘操纵状态才有效；bit0=1 时 vision_state 必须为 TRACKING（3）。置信度是否可用单独由 bit2 表示。未知置信度为 65535 且 bit2=0。

未检测到方向盘时清 bit0/bit1，两个操纵量均填 -32768；不能填 0 表示回中。检测到但定位无效或样本过期时清 bit0，两个操纵量同样填无效，bit1 只表达检测结果。此区块报告线下指定的主相机/融合定位结果，不传图像或多相机独立列表。

## 7. 双路主备、时间戳与超时

1. 两路独立解帧和校验，机器人默认 A 主、B 备；共享一套请求去重、控制接纳时间戳及状态机。离散有效请求从任一健康路进入同一请求表，只执行一次。
2. 本次运行连接内按 `(消息类型, timestamp_ms)` 识别逻辑消息，依第 2.1 节模运算判断新旧。CONTROL 首条目标还须满足本次 START_CONTROL 的时间边界。超时或重启后停止操控；普通短时切路不清基准。需重建基准时由双方受控协调停止有效控制/请求、核对未决动作、清空串口及应用队列，之后重建接收基准和去重表，再用新 START_CONTROL 开始操控。无线上启动标识，不能承诺自动识别所有重启，也不能据时间戳变小自动恢复。
3. 双路同一逻辑时间戳内容完全相同，只接纳一次。建议缓存最近 16 个周期的完整帧以比较副本；同时间戳且校验通过的内容不同，锁存冲突并撤销操控，不能仅凭主路优先断言正确。迟到副本发现冲突也处理，但不能撤销已经发生的运动。
4. 本路 60 ms 未收到递增、格式及语义有效的周期消息，或连续 3 次校验/格式/UART 错误，标为异常。机器人按 CONTROL 判断接收链路，飞控按 STATUS 判断接收链路；CONTROL 的 valid=0 可证明通信存活，不能证明控制输入有效。
5. 备路连续收到至少 10 个有效递增周期帧后可作为候选。主路异常时切到合格备路；切换只采用尚未提交的新时间戳。原主路恢复后保持备用，不自动抢占回切。
6. CONTROL 状态下全局 100 ms 没有新接纳的 valid=1 控制，关闭操控接纳并通知 Core 进入冻结的安全处理。切路不得清零全局超时；新开始操控后才能恢复，不以相同旧目标续命。
7. 飞控连续 100 ms 无有效新 STATUS，停止发有效控制和新动作请求，继续发送 valid=0 的 CONTROL 供观察。机器人 flags bit2/bit3 回报两路接收健康，飞控结合自己对应路 STATUS 接收情况识别单向故障；无需单独心跳或逐帧回复。
8. 各端串口发送队列有界：周期数据覆盖尚未发送的旧周期数据，禁止断线后补发历史周期帧；REPLY 优先于周期帧且不可被覆盖。独立本地 watchdog 不因日志或串口阻塞停转。

本简化版携带自增时间戳，但没有跨机时间同步，超时使用本地接收时间，不能仅凭时间戳排除“持续递增但已积压”的历史控制流。实现须直接接入串口、有界队列、发送前丢弃已等待 20 ms 的周期数据，并验证端到端延迟；不能把未知延迟的网络转串口桥当作等价链路。STATUS 不再携带采样年龄；机器人负责源数据时效检查，接收端另外考虑已验收的链路延迟及本地驻留时间。

周期消息存活、切换和控制失效的门限是台架建议，不是物理停止时间承诺；保持、制动、卸力或释放由 Core 和设备安全策略决定，网关不擅自回中或松手。

## 9. 带宽与实现映射

每路、每方向单独计算，双路不分摊数据。8N1 每字节占 10 bit：

| 方向 | 周期消息 | 计算 | 带宽 |
| --- | --- | --- | ---: |
| 飞控→机器人 | CONTROL | 14 字节×50 Hz×10 | 7000 bit/s |
| 机器人→飞控 | STATUS | 82 字节×50 Hz×10 | 41000 bit/s |

在 921600 下分别约占 0.8% 和 4.4%；另按 REQUEST/REPLY 各 10 帧/s 的含重试调度预算，分别增加 1000/1300 bit/s。STATUS 单帧线路时间约 0.89 ms，不存在转义膨胀。在 115200 下 STATUS 约占 35.6%，加上述 REPLY 预算约占 36.7%；如需采用该速率，须同时验证单帧约 7.12 ms 的传输时间及调度延迟，再由双方冻结。

Gateway 解码 CONTROL 后统一转换为内部 `flight.command`，roll/pitch 除以 10000；REQUEST 转为 Core 高层操作服务。Core 实际受理产生 REPLY，实际聚合反馈产生 STATUS。内部可保留原有详细会话、时间、诊断字段，不要求全部放入串口。

当前内部 FLIGHT 授权、高层操作服务、双手/视觉测量及串口仲裁仍需实现；关节位置量化只发生在 Gateway 边界。内部保留原始精度，不能直接把串口定点数组当内部浮点单位使用。日志记录原始 RX/TX、请求结果、拒绝原因和切路事件。

### 9.1 内部请求应答与数据记录边界

REQUEST 通过 Gateway → Core 独立 ZMQ 高层操作服务处理，不混入 `flight.command` PUB/SUB。接口、六个操作映射及错误处理见 [内部 ZMQ 协议第 14.5 节](AVIATOR_ZMQ协议格式说明.md#145-rs422-gateway--core-高层操作服务新增设计待实现)。Core 实际受理/同步完成/拒绝后，Gateway 生成并缓存首条逻辑 REPLY；长动作完成只更新 STATUS 并记录内部最终结果，不追加串口应答。ZMQ 发送成功、日志入队或持久化成功均不代表 Core 已受理。

Gateway 在本次受控建立的运行连接内维护 `(连接 ID, timestamp_ms)` 到内部 request_id 的映射，登记后才派发；比较完整请求内容，A/B 副本及全部重试不生成新动作身份。连接 ID 和内部 UUID 不在线上传输，不改变四类消息的长度。pending 请求的副本不重复派发新动作；已有应答重发原字节。内部超时保留未决身份，不伪造成功或确定拒绝，按第 3.3 节处理结果未知。建议 100 ms 是受理应答的端到端预算，不是机械动作完成期限。

Logger 总线订阅只能记录连续命令/状态；独立服务由 Gateway/Core 的记录适配器另送记录通道。必须记录原始串口 RX/TX、A/B 物理副本、重试/去重决定、内部完整请求/响应、Core 最终结果和事务映射。原始 TX 的驱动接纳不等于飞控收到；飞控时间戳仅用于关联，不与机器人运行时间相减计算延迟。服务记录的确认补传、缺口报告及 MCAP 关联遵循内部 ZMQ 协议第 15.5 节；当前这些适配器和串口运行入口尚待实现。

日志不参与串口一问一答：REPLY 不等待 Logger 确认，Logger 故障不阻塞安全退出。普通记录模式可能丢失；启用服务记录持久化补传也不等于原始串口帧无损。完整性按数据源独立验收，故障窗口、缺失和未决事务明确报告，不以 system.event 摘要代替完整服务记录。

## 10. 编码向量与联调验收

以下 Python 标准库示例给出四类帧长度和 CONTROL 校验和，可离线直接执行。CONTROL 示例使用 timestamp_ms=1000、roll=0.35、pitch=-0.12、valid=1；测试值不代表已取得实际授权。

```python
import struct

LENGTHS = {0x01: 5, 0x02: 8, 0x03: 9, 0x04: 77}

def encode(kind, data):
    assert len(data) == LENGTHS[kind]
    body = bytes([len(data) + 5, kind]) + data
    return b'\xff\xfe' + body + bytes([sum(body) & 0xff])

request = encode(0x01, struct.pack('<IB', 980, 3))
reply = encode(0x02, struct.pack('<IBBH', 980, 3, 1, 0))
control = encode(0x03, struct.pack('<IhhB', 1000, 3500, -1200, 1))
assert control.hex(' ') == (
    'ff fe 0e 03 e8 03 00 00 ac 0d 50 fb 01 01'
)
assert struct.calcsize('<IIBBHHBBB') == 17  # 系统区块
assert struct.calcsize('<7h') == 14         # 单臂，仅关节位置
assert struct.calcsize('<6h') == 12         # 单手，仅关节位置
assert struct.calcsize('<BBHhh') == 8        # 视觉区块
assert 17 + 14*2 + 12*2 + 8 == 77
# 方向盘反馈与 CONTROL 对应字段采用相同 int16 小端编码。
vision = struct.pack('<BBHhh', 3, 7, 9000, 3500, -1200)
assert vision[4:8] == control[8:12] == bytes.fromhex('ac 0d 50 fb')
# 仅测试帧长度/校验，不作为有效业务状态使用。
status = encode(0x04, bytes(77))
assert [len(f) for f in (request, reply, control, status)] == [10, 13, 14, 82]
def newer(new, old):
    delta = (new - old) & 0xffffffff
    return 0 < delta < 0x80000000

assert newer(0, 0xffffffff)
assert not newer(0xffffffff, 0)
assert not newer(1000, 1000)
assert not newer(0x80000000, 0)
for frame in (request, reply, control, status):
    assert frame[2] == len(frame)
    assert frame[-1] == (sum(frame[2:-1]) & 0xff)
```

| 场景 | 验收点 |
| --- | --- |
| 正常持续运行 | 只有四种 TYPE；CONTROL/STATUS 各 50 Hz；STATUS 每帧包含全部设备。 |
| 帧边界 | 拆包、粘包、数据内 FF FE、损坏长度、错误校验、半帧超时均正确处理。 |
| 一问一答 | 一个请求一条逻辑 REPLY；长动作由 STATUS 的状态/阶段观察进展，无异步完成应答。 |
| 丢应答/双路副本/重试 | 同请求只执行一次，重发原应答。 |
| 内部服务应答 | 发布成功不回成功；Core 决策才产生 REPLY；内部超时保持结果未知；长动作完成不追加 REPLY。 |
| 指令记录闭环 | 串口请求、内部请求、Core 决策、设备子请求及串口应答可按事务映射关联；每次物理重试可追踪。 |
| 记录故障 | Logger 断连/重启、确认丢失、慢盘和缓存耗尽按模式补传或报告缺口，安全退出不受阻塞。 |
| 定点边界 | 关节位置正负值、半步舍入、无效哨兵及超量程正确。 |
| 方向盘类型一致性 | 与 CONTROL 使用相同 int16 小端格式、比例和方向映射；检测失效不解释为零目标。 |
| 反馈缺失 | 无手部/相机数据仍保留全部槽位，填无效，不能填零冒充实测。 |
| 断 A/断 B/单向断线 | 接收健康正确、合格备路切换，双路失败撤销操控。 |
| 同时间戳不同内容 | 双路冲突锁存，不能重复执行或盲选主路。 |
| 重复/时钟回拨/重启/积压 | 重试时间戳不变、32 位回绕比较正确、重启从 0 计时但须受控重建连接，旧队列不补发。 |
| 重启/退出/重开操控 | 本次连接内旧控制和已登记请求不重做；跨重启未决请求不自动续发，由受控恢复核对。 |
| 发布与采样不同频率 | 保持 50 Hz 完整反馈，机器人内部检查采样时效，视觉过期清有效位，双臂/双手过期位置置无效。 |

冻结前确认实际双手关节数及量纲、量化范围/精度、方向盘方向映射、超时与安全动作、运行计时起点、回绕窗口、请求缓存及受控恢复方式。验收分别记录故障检测、主备切换、授权撤销及物理停止时间。
