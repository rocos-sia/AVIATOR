# AVIATOR 软件版本号规范

版本：V1.0  
日期：2026-10-11  
状态：已确认方案；运行代码和发布流水线按本规范接入。

## 1. 适用范围

AVIATOR 正式交付软件统一使用 `vMAJOR.MINOR.PATCH`，例如 `v1.0.3`。RS422 软件版本字段保持 2 字节，采用 **4 位主版本、4 位次版本、8 位修订号**，按 **uint16 小端**发送。

系统版本覆盖本次交付的 Core、Gateway、设备节点、运行脚本、随包依赖、模型和配置，不单独代表某个进程。各组件的构建信息可以保留，但对飞控上报的是整套发布版本。

本规范替代 ICD 中“高 8 位主版本、低 8 位小版本”的旧定义。当前帧布局见 [RS422 通信协议规范](AVIATOR_RS422通信协议规范.md)，软件内容校验见 [软件校验码规范](AVIATOR软件校验码规范.md)。

## 2. 命名和递增规则

| 分量 | 名称 | 递增条件 | 示例 |
| --- | --- | --- | --- |
| MAJOR | 主版本 | 通信接口、命令含义、状态/故障语义或配置格式发生不兼容变化。 | `v1.3.5 → v2.0.0` |
| MINOR | 次版本 | 增加功能，保持已声明接口向后兼容。 | `v1.3.5 → v1.4.0` |
| PATCH | 修订号 | 向后兼容的缺陷修复、稳定性改进或交付内容修订。 | `v1.3.5 → v1.3.6` |

1. `v` 是显示名称和 Git 标签前缀；CMake 等机器可读版本使用 `1.0.3`，不带 `v`。三个分量均为十进制整数，不加前导零，例如使用 `v1.2.3`，不使用 `v01.02.003`。
2. 增加主版本时，次版本和修订号归零；增加次版本时，修订号归零。按三个整数比较版本，不能按字符串排序。
3. `v0.x.y` 用于初始开发；正式稳定交付从 `v1.0.0` 开始。确定首个发布号是发布行为，本规范不自动修改当前项目版本。
4. 正式版本发布后，已交付内容不可覆盖。程序、依赖、模型或纳入软件校验的配置改变时，分配新版本并重新计算校验值；完全相同的已发布文件可原样重新分发。
5. 兼容性以对外协议和声明的运行契约判断，不能仅按修改代码行数决定。改变控制含义或安全约束的参数调整需评估兼容性，不能一律视为 PATCH。
6. Git 提交号、构建工具链、依赖版本及发布配置单独记录，不挤入 16 位版本字段。版本号说明发布次序与兼容性，SHA-256 标识具体交付内容，两者相互补充。

命名与基本递增原则参考 [Semantic Versioning 2.0.0](https://semver.org/)。本项目额外施加下面的串口字段容量限制。

## 3. RS422 编码

### 3.1 位分配

| 位段 | 内容 | 允许范围 |
| --- | --- | --- |
| bit15～bit12 | MAJOR | 0～15 |
| bit11～bit8 | MINOR | 0～15 |
| bit7～bit0 | PATCH | 0～255 |

```text
version_u16 = (MAJOR << 12) | (MINOR << 8) | PATCH

MAJOR = (version_u16 >> 12) & 0x0F
MINOR = (version_u16 >> 8)  & 0x0F
PATCH = version_u16 & 0xFF
```

这是二进制位分配，不是 BCD，也不是将字符串 `1.0.3` 直接发送。取值超出范围时，构建/发布检查必须失败，不截断、不回绕、不为迁就容量而擅自改变语义化递增规则；需要先扩展协议或重新确认版本策略。

### 3.2 字段位置与字节序

当前上行帧长度为 29 字节，偏移从 0 开始：

| 偏移 | 内容 |
| ---: | --- |
| 22 | `version_u16 & 0xFF`，即 PATCH。 |
| 23 | `(version_u16 >> 8) & 0xFF`，高半字节为 MAJOR，低半字节为 MINOR。 |

| 软件版本 | uint16 数值 | 字节 22 | 字节 23 |
| --- | --- | --- | --- |
| `v1.0.3` | `0x1003` | `03` | `10` |
| `v1.2.15` | `0x120F` | `0F` | `12` |
| `v2.0.0` | `0x2000` | `00` | `20` |
| `v15.15.255` | `0xFFFF` | `FF` | `FF` |

`0xFFFF` 是合法版本 `v15.15.255`，不是未知值。`0x0000` 对应 `v0.0.0`，也不能冒充“版本未知”。发布元数据缺失或校验失败时，应阻止进入可操控状态并报告诊断，不伪造版本；尚未冻结的串口异常表示不由本字段隐式承担。

## 4. 正式版与测试版

正式交付只使用无后缀版本，例如 `v1.0.3`。开发/台架测试可使用 `v1.0.3-rc.1` 等预发布标签；Git 提交号等可作为独立构建信息或构建元数据保存。

16 位字段不能区分 `v1.0.3-rc.1` 与 `v1.0.3`。因此正式运行发布检查必须拒绝带预发布后缀的产物；台架若使用预发布产物，需在台架配置和界面明确标识，不将其声明为正式版。不得占用版本字段中的合法位来偷偷表达测试标志。

## 5. 版本来源与发布信息

复用现有 [CMakeLists.txt](../CMakeLists.txt) 的 `project(AVIATOR VERSION ...)` 作为唯一版本源。后续接入时，由构建/发布步骤生成各程序的版本显示及机器可读发布信息，避免 Core、Gateway、界面和安装包分别手填。

建议随发布目录提供 `release-version.json`，并纳入软件内容校验，最小示例如下：

```json
{
  "product": "AVIATOR",
  "version": "1.0.3",
  "version_u16": 4099,
  "release_profile": "hardware"
}
```

正式记录还应包含实际 Git 提交号和工具链/依赖标识；不得将示例值当成当前构建事实。所有节点须来自同一发布目录；启动时核对各组件所属发布版本，发现混装不允许按完整发布声明就绪。

本文件中的示例版本不自动替代项目版本。版本生成已按 [版本与校验码实现方案](AVIATOR版本与校验码实现方案.md) 接入构建；混装检测和启动门控仍待运行链路接入。

## 6. 编解码参考与验收

```python
import struct

def encode_version(major, minor, patch):
    if any(type(v) is not int for v in (major, minor, patch)):
        raise ValueError("版本分量必须为整数")
    if not (0 <= major <= 15 and 0 <= minor <= 15 and 0 <= patch <= 255):
        raise ValueError("版本超出 4+4+8 位范围")
    return struct.pack("<H", (major << 12) | (minor << 8) | patch)

def decode_version(raw):
    value, = struct.unpack("<H", raw)
    return (value >> 12) & 15, (value >> 8) & 15, value & 255

assert encode_version(1, 0, 3).hex(" ") == "03 10"
assert decode_version(bytes.fromhex("0f 12")) == (1, 2, 15)
assert encode_version(15, 15, 255) == bytes.fromhex("ff ff")
```

验收至少覆盖：最小/最大分量、非法分量拒绝、三个示例的往返编解码、正式版后缀检查、各组件版本一致，以及串口偏移 22～23 和整帧校验正确。

旧 8+8 编码与新 4+4+8 编码不得混用。帧中没有编码方案自描述位，发送和接收两端需按部署版本同时切换；不根据码值猜测新旧格式。
