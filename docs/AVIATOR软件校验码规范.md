# AVIATOR 软件校验码规范

版本：V1.0  
日期：2026-10-11  
状态：已确认方案；发布和运行校验按本规范接入。

## 1. 目的与两种表示

AVIATOR 使用 **SHA-256** 核对正式交付内容，复用 `sha256sum`、CMake 或 Python 标准库等现有工具，不自行实现哈希算法。

| 表示 | 长度 | 用途 |
| --- | --- | --- |
| 完整系统摘要 | 256 bit，显示为 64 个小写十六进制字符 | 发布归档、交付验收和实际部署核对。 |
| RS422 短校验码 | 16 bit，uint16 小端 | 在上行周期帧中快速比对发布标识。 |

短码取完整摘要的**最左侧 4 个十六进制字符**，按十六进制整数解析后小端发送。它只有 65,536 种取值，允许发生碰撞，不能代替完整摘要验收，也不作为唯一的软件身份。

相关文件：[软件版本号规范](AVIATOR软件版本号规范.md)、[RS422 通信协议规范](AVIATOR_RS422通信协议规范.md)。ICD 中“编译器生成的校验码 0xABCD”由本规范替代；`0xABCD` 仅可作为示例，不能固定写入运行软件。

## 2. 校验对象

### 2.1 使用最终发布目录

校验对象为完成安装、动态库整理、裁剪调试信息和配置落盘之后的**最终发布文件**。不直接对 Git 提交号、源代码目录、编译中间件或内存中的运行镜像计算系统摘要。

默认纳入以下实际随包交付并参与运行的内容：

- Core、Gateway、Manipulator、手部、相机等已选择发布组件的程序和运行脚本。
- 随包动态库、算法资源、机器人模型和标定文件。
- 影响设备连接、控制、限位、保护和算法行为的交付配置。
- `release-version.json` 等版本和发布配置记录。

排除日志、缓存、临时文件、运行时状态、测试输出、`SHA256SUMS` 本身及保存系统摘要的文件。发布配置必须明确包含目录和排除项；不得将影响运行的配置随意排除来维持旧校验码。

不同硬件/仿真发布配置可以具有同一功能版本，但需使用不同发布配置标识和各自的完整摘要。现场修改校验范围内文件后，原发布身份失效，应重新发布并按版本规范分配版本。

### 2.2 文件内容与路径

本规范核对文件路径和内容，不覆盖文件权限、所有者、时间戳或整个操作系统。安装权限、外部系统依赖和硬件条件由部署检查另行验证。

路径使用发布根目录下的相对路径，统一 `/`，不得含绝对路径、`..` 路径段、反斜杠、回车或换行。路径按 UTF-8 字节序排序，不受操作系统地区设置影响。同一路径只出现一次，并禁止仅大小写不同的重复路径，以保证跨平台解释一致。

目录符号链接不纳入发布范围；文件符号链接只允许解析到发布根目录内的普通文件，以链接的相对路径记录、按实际目标内容哈希。发布校验须重新检查链接目标没有逃出根目录。内容相同的链接替换不改变内容摘要；如果需要验证链接结构或权限，需另加部署检查，不能宣称 SHA256SUMS 已覆盖。

## 3. 发布清单与系统摘要

### 3.1 SHA256SUMS 格式

对范围内每个文件计算完整 SHA-256，生成兼容 `sha256sum --check` 的 `SHA256SUMS`：

```text
<64个小写十六进制字符><两个ASCII空格><相对路径><LF>
```

清单采用 UTF-8、无 BOM、LF 换行，最后一行也有 LF。无标题、注释、空白行、绝对路径和生成时间。排序使用第 2.2 节规则。文件内容原样哈希，不转换换行或文本编码。

### 3.2 系统摘要的计算

```text
file_digest[i] = SHA256(发布文件 i 的实际字节)
SHA256SUMS    = 按规定排序与编码生成的清单字节
release_digest = SHA256(SHA256SUMS 的实际字节)
```

清单中的文件内容摘要和相对路径共同决定系统摘要；改名、增加或删除纳入范围的文件也会改变系统摘要。相同最终文件、路径和清单格式在不同机器上应产生相同结果。重新编译若产生不同二进制字节，摘要变化是正确结果；本规范不自动保证编译过程可复现。

保存 `release_digest`、16 位短码及算法标识 `SHA256SUMS-v1` 的发布元数据不参与本次清单计算，避免自引用。不要把最终摘要回写到已经参与哈希的可执行程序；如需程序显示摘要，在启动校验后读取独立元数据。

## 4. RS422 短码

```text
H = release_digest 的 64 字符十六进制表示
checksum_u16 = int(H[0:4], 16)

字节24 = checksum_u16 & 0xFF
字节25 = (checksum_u16 >> 8) & 0xFF
```

当前上行帧共 29 字节，偏移从 0 开始。**先取摘要前 16 位，再把所得整数按小端发送**；不是直接复制摘要的前两个原始字节，也不是取十六进制字符串的最后 4 位。

| 完整摘要开头（示例） | 短码数值 | 字节 24～25 |
| --- | --- | --- |
| `abcd…` | `0xABCD` | `CD AB` |
| `ba78…` | `0xBA78` | `78 BA` |
| `0000…` | `0x0000` | `00 00` |

`0x0000`、`0xFFFF` 都可能是合法短码，不保留为未知或失败标志。短码与完整摘要都必须关联对应的软件版本和发布配置；即使版本和短码一致，验收仍需核对完整摘要。

软件短码参与整帧累加校验：上行字节 26 为字节 0～25 的累加补码，字节 27～28 为帧尾。**软件 SHA-256 与通信帧累加校验是两个独立计算**，不能互相替代。

## 5. 工具与流程

### 5.1 复用工具

| 环境 | 生成完整 SHA-256 | 校验已有清单 |
| --- | --- | --- |
| Linux / GNU 工具 | `sha256sum 文件路径` | 在发布根目录执行 `sha256sum --check --strict SHA256SUMS`。 |
| Windows PowerShell | `Get-FileHash -Algorithm SHA256 -LiteralPath 文件路径` | 按清单遍历计算并比较；输出转为小写后与规范文本比较。 |
| CMake | `file(SHA256 "文件路径" digest)` | 在发布脚本中逐项校验。 |
| Python 标准库 | `hashlib.sha256` | 实现清单排序、范围检查和校验包装，不实现哈希算法本身。 |

工具依据：[GNU SHA-2 utilities](https://www.gnu.org/s/coreutils/manual/html_node/sha2-utilities.html)、[CMake file HASH](https://cmake.org/cmake/help/latest/command/file.html#hash)、[Python hashlib](https://docs.python.org/3/library/hashlib.html)。

工具默认输出格式不一定等于规范清单；生成清单时统一小写摘要、两空格分隔、UTF-8/LF 和排序。`sha256sum --check` 只验证列出的文件，不会自动发现多出的文件，因此发布/启动包装检查还必须比对实际纳入范围的路径集合，拒绝缺项、多项、重复路径和目录越界。

### 5.2 发布时

1. 冻结软件版本、Git 提交、依赖和发布配置，完成最终文件整理。
2. 在不再变化的发布目录上枚举范围内文件，生成 `SHA256SUMS`。
3. 验证清单与文件集合一致，逐文件核对；对清单计算 `release_digest` 和短码。
4. 保存版本、发布配置、清单、完整摘要和短码，形成交付记录。完整摘要通过可信交付记录交给验收方。
5. 打包后可额外对压缩包计算 SHA-256，用于检查下载/传输完整性；该值属于“安装包摘要”，不替代本规范的“系统摘要”，也不直接填入 RS422 字段。

### 5.3 部署验收和运行时

验收方先核对 `SHA256SUMS` 的系统摘要与可信交付记录一致，再检查实际文件集合及各文件内容。只验证清单中自带的哈希不足以证明发布者身份；需要防止恶意替换时，应对交付记录或清单使用数字签名。

启动时完成实际部署校验，成功后缓存版本和短码，供 Gateway 每 12.5 ms 上报一次；不能只读取一个预置短码就声称运行文件通过验证，也不应在每个串口周期重新扫描磁盘。校验未完成、失败或发布元数据缺失时，不进入可操控状态，并保留诊断；本规范不擅自分配新的故障码或未知值，相关异常线上表达需在 ICD 中补齐。

运行期间发布文件应保持不变。更新必须按部署流程停止相关节点、替换完整发布、重新验证后启动；启动校验不等于持续监测内存或文件篡改。发生变化后旧缓存不能代表新内容。

## 6. 算法测试向量与验收

下面的 `abc` 是**哈希与字节序算法测试输入**，不是实际软件发布清单。它用于验证“前 16 位”和小端规则，真实系统摘要必须按第 3 节计算。

```python
import hashlib
import struct

def checksum16(full_digest):
    if len(full_digest) != 64 or any(c not in "0123456789abcdef" for c in full_digest):
        raise ValueError("需要64字符小写SHA-256摘要")
    return int(full_digest[:4], 16)

digest = hashlib.sha256(b"abc").hexdigest()
assert digest == "ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad"
assert checksum16(digest) == 0xBA78
assert struct.pack("<H", checksum16(digest)).hex(" ") == "78 ba"
```

| 验证项 | 预期 |
| --- | --- |
| 同文件、路径和清单格式 | 跨机器计算完整摘要和短码一致。 |
| 文件修改、删除、改名或增加 | 文件校验或路径集合检查失败，不仍声明原发布通过。 |
| 日志或缓存变化 | 不改变发布文件清单和系统摘要。 |
| 清单换行/BOM/排序变化 | 拒绝非规范清单；不在校验前自动改写后掩盖差异。 |
| 前 16 位 | 使用最左 4 个十六进制字符，`ba78… → 0xBA78 → 78 BA`。 |
| 内容核对 | 完整摘要匹配可信交付记录，且实际文件逐项通过，才算通过。 |
| 运行上报 | 使用成功校验后的缓存；位置为上行 24～25，不阻塞 80 Hz 周期。 |

当前仓库尚未因本规范自动新增发布生成器、运行验证或串口上报代码；上述步骤是后续实现与验收要求。
