# AVIATOR 提交版本维护

从 Git 仓库根目录执行。先阅读 `docs/AVIATOR软件版本号规范.md`；涉及发布内容或测试校验码时，同时阅读 `docs/AVIATOR软件校验码规范.md` 和 `docs/AVIATOR版本与校验码实现方案.md`。

- 三段数字版本的唯一来源是根 `CMakeLists.txt` 的 `project(AVIATOR VERSION ...)`，不维护第二份三段版本常量，不提交 build/install 产物。内部测试后缀独立记录，不写入该 CMake 版本或 RS422 字段。
- 仅在用户要求创建 Git 提交时执行本流程；每次创建提交都需维护版本，包括纯文档、测试和工具维护。普通编辑、构建和校验不升级版本。
- 先查看实际待提交差异（包括配置、脚本、依赖、模型），再确认更新类型：用户指令已明确“内部测试更新”或“PATCH 更新”时直接采用，不重复询问；未明确时，询问本次属于哪一类，收到答复后再确定最终版本号。不得擅自默认 PATCH，也不得仅因存在功能新增或不兼容变更就自动升级 MINOR 或 MAJOR。
- 内部测试更新：保持 HEAD 中的 MAJOR.MINOR.PATCH 不变，只递增测试标识，默认使用 `rc.N`。读取当前分支历史中同一三段版本最近的测试标识，将 N 加一；没有已有标识时从 `rc.1` 开始。例如 `v7.0.0 → v7.0.0-rc.1 → v7.0.0-rc.2`。用户已确认此规则，不再每次询问测试号格式；仅在指令另有要求或历史记录存在歧义时确认。
- 测试标识通过内部测试提交说明末尾的 trailer `AVIATOR-Test-Version: vMAJOR.MINOR.PATCH-rc.N` 持久记录，供后续提交读取，不需要创建 Git 标签或修改运行时版本机制。该标识用于提交追踪；当前构建和串口仍只有三段数字版本，不能据此宣称产物已支持预发布后缀识别。
- PATCH 更新：以 HEAD 三段版本为基线，保持 MAJOR、MINOR 不变，PATCH 加一，最终版本不带测试后缀，也不写入测试版本 trailer。例如 `v7.0.0-rc.2 → v7.0.1`。新三段版本后续若进入内部测试，从 `rc.1` 开始。
- 兼容性检查仍需说明实际影响：MAJOR 对应接口、命令、状态/故障语义、配置格式或控制安全契约不兼容；MINOR 对应向后兼容新增功能；PATCH 对应兼容修复及交付内容修订。若所选更新类型与正式交付的兼容性规则冲突，说明冲突并请用户确定处理方式，不自行改变已选类型。用户明确要求 MAJOR、MINOR 或具体版本时按其指令处理；提高高位时将低位归零。
- 新提交以 HEAD 中版本为基线；若待提交版本或本次提交说明中的测试标识已按已确认规则正确升级，本次不再次递增。失败重试不重复升级。amend 保持该提交已分配的三段版本及测试标识；若用户改变更新类型或明确要求重新定版，相对父提交按上述确认流程重新确定，不自动升级 MAJOR 或 MINOR。
- 检查 MAJOR <= 15、MINOR <= 15、PATCH <= 255，十进制且无前导零。溢出时停止提交并说明原因，不自动进位掩盖语义，不截断或回绕。用户明确指定版本时优先遵从，同时检查规范合法性。
- PATCH 或明确要求的 MAJOR/MINOR 更新，将版本修改与本次业务差异一起暂存。内部测试更新只记录新的测试标识，不为递增版本而修改 CMakeLists.txt；用户明确要求重设三段版本时，以指定版本为基线确定测试标识，并一并提交 CMake 版本修改。若根 CMakeLists.txt 还有不属于本次提交的编辑，仅暂存本次相关片段，保留其他编辑。不得把未授权的其他文件带入提交。
- 确定类型和递增规则后，在提交前说明更新类型、原版本（含已有测试标识）、最终版本及依据。指令和已确认规则足以确定最终版本时直接执行；仍有歧义时先询问，不在版本未确定时创建提交。使用 `python3 tests/release_test.py` 验证版本/校验规则；提交后核对三段版本，内部测试提交还需核对测试版本 trailer。
- 本 skill 不创建发布标签、不推送、不自动发布。构建与安装计算内容摘要，但不递增版本。
